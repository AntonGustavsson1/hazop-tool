Varför ökar $\lambda_{DU}$ i koden?  En repa i sätet orsakar ett mikroläckage. I applikationen Full_Stroke ignoreras detta eftersom ventilen stänger. Men i Tight_Shut_Off klassas denna felmod programmeringstekniskt om från Safe/Ignored till Dangerous Undetected ($\lambda_{DU}$), vilket förklarar hoppet från 479 FIT till 1370 FIT i databasen.  2. Markov-modellering i kod (Hantering av PST på TSO)exida använder ofta diskreta Markov-kedjor istället för förenklade formler när komplex diagnostik (som PST) blandas in.  Vid en vanlig Full Stroke-ventil kan ett PST-test ha en Diagnostic Coverage (DC) på ca 70 %. Men ett PST-test kan aldrig upptäcka läckage. Därför måste din beräkningsmotor beräkna en viktad (effektiv) DC baserat på applikationskravet.  Här är en algoritm som beräknar den exakta dämpningen av $PFD_{avg}$ över tid ($t$):Pythonimport numpy as np

def calculate_pfd_curve(lambda_du_base, dc_pst, interval_pst_hours, interval_fst_hours, total_years=5):
    """
    Simulerar PFD-utvecklingen timme för timme baserat på exidas två-nivåers testmodell.
    """
    total_hours = total_years * 365 * 24
    time_axis = np.arange(0, total_hours, 1)
    pfd_axis = np.zeros(total_hours)
    
    # Omvandla FIT till fel per timme
    lambda_du = lambda_du_base * 1e-9
    
    # Dela upp felen i vad PST kan hitta (stroke) vs vad som förblir dolt (leakage)
    lambda_DD_pst = lambda_du * dc_pst        # Hittas vid varje PST-intervall
    lambda_DU_rest = lambda_du * (1 - dc_pst)   # Hittas bara vid full turnaround (FST)
    
    for t in time_axis:
        # Räkna ut dötid sedan senaste testerna (så kallad sawtooth-wave)
        time_since_pst = t % interval_pst_hours
        time_since_fst = t % interval_fst_hours
        
        # PFD för de två parallella feltyperna enligt exidas modeller
        pfd_pst_part = lambda_DD_pst * time_since_pst
        pfd_fst_part = lambda_DU_rest * time_since_fst
        
        # Total PFD vid tidpunkt t
        pfd_axis[t] = pfd_pst_part + pfd_fst_part
        
    return time_axis, pfd_axis, np.mean(pfd_axis)

# --- SIMULERING / JÄMFÖRELSE ---

# Scenario 1: Standard Full Stroke ventil med PST (DC = 70% på mekaniken)
_, _, pfd_avg_full_stroke = calculate_pfd_curve(
    lambda_du_base=479, dc_pst=0.70, interval_pst_hours=730, interval_fst_hours=26280

# Effektiva DC blir då: 149 / 1370 = ~11%
effective_dc_tso = 149 / 1370

_, _, pfd_avg_tso = calculate_pfd_curve(

)

print(f"Genomsnittlig PFD (Full Stroke + PST): {pfd_avg_full_stroke:.6f}")
print(f"Genomsnittlig PFD (Tight Shut-Off + PST): {pfd_avg_tso:.6f}")
3. Vad koden avslöjar om exidas logikOm du kör simulationen ovan kommer du att se att pfd_avg_tso blir markant mycket högre. Detta beror på två programmeringstekniska regler som exSILentia tillämpar:  Den dolda potten dominerar: Eftersom effective_dc_tso kollapsar till drygt 11 % (eftersom merparten av felen på en TSO-ventil är sätesskador som kräver FST), ackumuleras nästan hela felfrekvensen på 1370 FIT i den långsamma cykeln (interval_fst_hours = 3 år).  PST-funktionen "mättas": Att köra PST oftare (t.ex. varje vecka istället för varje månad) ger nästan ingen mätbar effekt på en TSO-ventil i programmet, eftersom kurvan styrs av sätets läckagerisk.  4. Hur man bygger "Arkitektur-spärren" (SFF/HFT-kontrollen)Mjukvaran räknar inte bara PFD, den måste också validera "Barrier 2" (Minimum Architectural Constraints) enligt IEC 61508 Route 1H. Om din kod upptäcker att SFF (Safe Failure Fraction) sjunker under en viss gräns, måste programmet kasta en varning och tvinga användaren att bygga ett redundant system (t.ex. 1oo2 d.v.s. dubbla ventiler).  Här är en enkel valideringsmodul:Pythondef verify_architectural_constraints(lambda_sd, lambda_su, lambda_dd, lambda_du, target_sil):
    # Beräkna Safe Failure Fraction (SFF)
    total_failures = lambda_sd + lambda_su + lambda_dd + lambda_du
    if total_failures == 0:
        return "Invalid Data"
        
    sff = (lambda_sd + lambda_su + lambda_dd) / total_failures
    
    # För mekaniska komponenter (Typ A-enheter enligt IEC 61508) gäller:
    # HFT = 0 (Enkelventil) kräver:
    # SIL 2 -> SFF mellan 60% och 90%
    # SIL 3 -> SFF > 90%
    
    if target_sil == 2:
        if sff >= 0.60:
            return f"GODKÄND för SIL 2 med singelventil (HFT=0). SFF: {sff*100:.1f}%"
        else:
            return f"UNDERKÄND för SIL 2. SFF ({sff*100:.1f}%) är för låg. Kräver redundans (HFT=1, t.ex. 1oo2)!"
            
    elif target_sil == 3:
        if sff >= 0.90:
            return f"GODKÄND för SIL 3 med singelventil (HFT=0). SFF: {sff*100:.1f}%"
        else:
            return f"UNDERKÄND för SIL 3. SFF ({sff*100:.1f}%) är under 90%. Du MÅSTE konfigurera redundanta ventiler."

# Exempel på körning för TSO-ventilen utan diagnostik (SFF blir 0% eftersom alla fel är DU)
print(verify_architectural_constraints(0, 0, 0, 1370, target_sil=2))
